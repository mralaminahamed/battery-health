Shipping to Google Play

Everything between the current repository state and a live listing — including two decisions that cannot be reversed once the first upload lands.

Package com.alaminahamed.batteryhealth Name Battery Health Version 0.1.0 (1) Flavour play minSdk 26 targetSdk 37

Read before anything else

Irreversible — decide now

The application ID is permanent from the first upload. Google Play keys a listing on its package name forever. It cannot be renamed, and a different ID is a different app: new listing, zero installs, zero reviews, no upgrade path for anyone who installed the old one.

Settled. The package is now com.alaminahamed.batteryhealth — renamed across 130 files in commit 7a9b2db, verified in the built bundle, and done before any upload. Nothing further is needed here; it is recorded because it is the one choice on this page that can never be revisited.

Blocks submission

The privacy policy needs a publicly reachable URL. The policy is written and committed at docs/privacy-policy.md, but this repository is private, so no GitHub link to it will resolve for a reviewer. Host it somewhere public before you reach step 13.

Unverified

The privileged tier — the ADB handshake, Keystore signing, the authorisation prompt — has never successfully run on real hardware. It is covered by 265 unit tests against a protocol-speaking fake daemon, which is not the same claim. Finishing the on-device pass before you publish is strongly advised.

Part one · Build a publishable artifact

01

Application ID: com.alaminahamed.batteryhealth

Decided and applied — commit 7a9b2db moved all five source sets and rewrote every reference. namespace and applicationId match, and the built bundle carries the new ID.

This had to happen before the first upload and it did. Play binds a listing to its package name on that upload and never lets it change.

02

App name: Battery Health

Decided. The store title is Battery Health — matching app_name in strings.xml, which already says exactly that. No code change is needed, and the launcher label and store listing now agree.

Why not "Samsung Battery Health"

Play's Impersonation policy forbids titles that suggest a relationship with another company that does not exist. A battery app named for Samsung, published by an individual developer, reads as first-party Samsung software — a clear-cut rejection, and a more likely one than the ADB question further down. "Galaxy" carries the same trademark and the same risk.

Device compatibility belongs in the description, where it is descriptive rather than claimed: "Works with Samsung Galaxy devices" is fine. The trademark in the title is not.

The known cost is discoverability — the name is generic, and Play enforces uniqueness on the package name rather than the title, so you will sit among many identical results. That is an acceptable trade for an internal-track release, and unlike the package name the store title can be changed later if you want something more distinctive once the app is proven.

03

Create the upload key

Generate it yourself and keep it out of the repository.

keytool -genkeypair -v \
  -keystore upload-keystore.jks \
  -alias upload \
  -keyalg RSA -keysize 4096 -validity 10000
Back this up

Losing the keystore means losing the ability to publish updates under this listing, permanently. Store a copy somewhere outside the repository and outside this machine. *.jks and *.keystore are gitignored so it cannot be committed by accident.

04

Wire the credentials in

cp keystore.properties.example keystore.properties
# then fill in storeFile, storePassword, keyAlias, keyPassword

keystore.properties is gitignored. For CI, set RELEASE_STORE_FILE, RELEASE_STORE_PASSWORD, RELEASE_KEY_ALIAS and RELEASE_KEY_PASSWORD instead — no file on disk is needed.

With nothing configured, release builds come out unsigned rather than falling back to the debug key. That is deliberate: Play rejects debug-signed uploads, and an unsigned artifact fails loudly instead of quietly shipping wrong.

05

Set the version

In app/build.gradle.kts. versionCode must increase on every single upload — Play refuses a code it has already seen, even on a closed track, and even for a build you deleted.

versionCode = 1 and versionName = "0.1.0" are fine for a first internal build.

06

Build the bundle

Play takes an .aab. An APK will be rejected at upload.

./gradlew clean :app:bundlePlayRelease

app/build/outputs/bundle/playRelease/app-play-release.aab

Build the play flavour, never full. The full flavour declares QUERY_ALL_PACKAGES, which Play does not accept for battery attribution; play deliberately omits it.

07

Verify it is actually signed

Cheaper to check here than to be rejected at upload.

unzip -l app/build/outputs/bundle/playRelease/app-play-release.aab \
  | grep -E 'META-INF/.*\.(RSA|DSA|EC)'

A match means signed. No output means unsigned — your credentials were not picked up, so go back to step 4.

Wording matters here

Do not claim the app reads state of health. It measures capacity by sampling charge counters, and reports unavailable when it cannot. A listing that overpromises invites both one-star reviews and a policy complaint about misleading claims.

12

App access — do not skip this one

Policy → App content → App access

The privileged tier is off until a user runs a setup step. A reviewer who launches the app cold sees most metrics reporting unavailable, and may reasonably conclude it is broken.

Choose All or some functionality is restricted and give the reviewer instructions:

Advanced battery metrics (state of health, first-use date) require a
one-time setup, because Android restricts them to system apps.

1. Enable Developer options, then USB debugging.
2. From a computer with adb installed, run:  adb tcpip 5555
3. Open the app and tap "Unlock more readings".
4. Approve the "Allow USB debugging?" prompt shown on the device.

No account or credentials are needed. Without this the app still works
and honestly reports the affected metrics as unavailable.

14

Data safety

Policy → App content → Data safety

Answers are prepared in docs/play-data-safety.md. The short version: the app collects and shares nothing. Play defines "collect" as transmitting off the device, and this app makes no outbound requests at all.

Expect the INTERNET permission to draw attention. The answer is that Android enforces it at socket creation regardless of destination and does not exempt loopback, so an app cannot talk to its own device without it — and a test fails the build if any source opens a socket that could reach anywhere else.

15

Foreground service declaration

Policy → App content → Foreground service permissions

The manifest already carries the required PROPERTY_SPECIAL_USE_FGS_SUBTYPE subtag — the part most submissions get wrong. Paste the matching justification verbatim: 

Samples battery charge counters every five seconds while charging to
measure full capacity, which cannot be derived from 15-minute periodic
work.

If pressed: WorkManager's floor is a 15-minute period, at which cadence charge-counter deltas are dominated by noise and the derived capacity is not trustworthy. No other foreground service type describes this use.

Closed test, then production

For a new personal developer account, production is gated behind a closed test with 12+ testers running 14 continuous days. Start that clock as early as you can — it is usually the longest item on this page.

Risks specific to this app

Policy · genuinely uncertain

An app that instructs users to enable ADB debugging and then acts as an ADB client against its own device sits in unsettled territory under Device and Network Abuse, which covers circumventing the Android permission model. Shizuku-based apps exist on Play, but this shape is different — the app is the client itself.

Two facts are worth having ready if it is questioned. The privileged surface is exactly two commands compiled in as constants, with no method anywhere accepting a command string, so it is structurally incapable of running anything else. And the tier is entirely optional — the app works without it and says so rather than estimating.

A rejection here is not fatal but costs a review cycle. The internal track lets you learn this cheaply.

Product

DesignCapacityTable holds exactly one entry — SM-A356. Every other device reports state of health as unavailable, which is honest but means most installs see the app's headline feature blank. Worth either expanding the table or setting expectations clearly in the listing before a public launch.

Order of work

Recommended sequence
  • Decide the package name. Free now, impossible later.
  • App name is settled: Battery Health. Matches the launcher label already; no trademark exposure.
  • Finish on-device verification. Do not ship an unproven core feature.
  • Host the privacy policy. Blocks submission outright.
  • Keystore, then bundle, then internal track. Cheapest way to learn what breaks.
  • Screenshots and feature graphic. Only worth the effort once the app is proven.
  • Start the 14-day closed test. The long pole — begin it early.
